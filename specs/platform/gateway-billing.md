# 模型网关与计费

平台侧的模型流量入口。所有平台管理的模型调用都经过这里：在这里鉴权、判权限、预扣、转发、计量、结算。**这是商业模式的强制点**。

## 为什么必须在服务端

客户端在用户手里，可以被修改。因此：

- 上游厂商 API key 只存在于网关，永不下发到客户端。
- 余额是否足够、套餐是否包含该模型，只在网关判定。
- 用量的权威记录只在网关。客户端本机的 `model_usage` 表仅用于本机统计展示，不参与计费。

## 请求链路

```
客户端 agent
  → 解析 provider 配置，得到 baseUrl = <platformOrigin>/api/v1/gateway/<providerId>
  → transport 层判断目标 origin 是平台网关时，注入 Authorization: Bearer <用户令牌>
  → 网关收到请求
      1. 验令牌 → 得到 userId
      2. 校验请求路径在上游白名单内（审计#3）
      3. 解析请求体：模型名与 max_tokens
      4. 校验用户状态、套餐对该模型的权限
      5. 校验模型已配单价（审计#4）
      6. 原子预扣：同一 BEGIN IMMEDIATE 事务内算可用额度并写 reserved（审计#7）
      7. 转发到真实上游（注入平台 key；OpenAI 流式补 stream_options.include_usage，审计#2）
      8. 从响应中取 usage（流式取 SSE 末尾事件）
      9. 原子结算：状态改终态 + 套餐扣减 + 余额流水在同一事务（审计#6）
```

任一步失败都在**转发之前**返回，不产生上游费用：

- 令牌无效 → `401`
- 用户停用 → `403`
- 路径不在白名单 → `404 path_not_allowed`
- 套餐不含该模型 → `403 model_not_entitled`
- 模型未配单价 → `403 model_not_priced`
- 余额不足 → `402 insufficient_balance`
- 同一 `request_id` 重复 → `409 duplicate_request`

## 上游路径白名单（审计#3）

网关不是任意路径的透传代理，只放行各协议已知的端点，其余一律 `404 path_not_allowed`
（请求路径不在网关前缀下时是 `404 path_not_found`）。这样客户端无法把网关当成访问上游任意 API 的跳板。

| 协议                           | 计费端点                                                                   | 不计费辅助端点                            |
| ------------------------------ | -------------------------------------------------------------------------- | ----------------------------------------- |
| `anthropic`                    | `/v1/messages`                                                             | `/v1/messages/count_tokens`、`/v1/models` |
| `openai` / `openai-compatible` | `/chat/completions`、`/v1/chat/completions`、`/responses`、`/v1/responses` | `/models`、`/v1/models`                   |

OpenAI 兼容端点同时接受带 `/v1` 前缀的写法：第三方客户端用平台 API Key 时按 SDK 惯例把
base_url 配成 `.../v1`，请求路径会自带前缀；转发时路径原样上送，最终地址由上游 baseUrl 决定。
两条写法都按计费端点处理（含 include_usage 注入），不能出现"带 /v1 就绕开计费"的旁路。

辅助端点仍然注入平台 key 并转发，但不解析模型、不查价、不预扣、不结算，也不出现在用量记录里。
计费端点必须有请求体里的 `model`，且该模型在 `prices` 里有单价，否则 `403 model_not_priced`
（审计#4）——未配单价的模型按 0 计费等于白送上游成本。

## 计费口径

- 按 token 计价，单价由管理员按模型配置：输入、输出、缓存读取、缓存写入四档，单位是"每百万 token 的价格"。
- 一次请求的费用 = 各档 token 数 × 对应单价之和。
- 扣费来源优先级：**先扣套餐内额度，额度用尽后再扣余额**。套餐额度按周期重置。
- **可用额度 = 余额 − 未结算预扣 + 当前有效订阅的剩余额度**（审计#5）。
  套餐用户即使余额为 0 也能用套餐额度调用；预扣与结算都按这个口径放行。
- 充值、套餐发放、管理员调整都写入 `ledger`，不允许直接改余额数字。余额是流水的派生结果，并可随时对账重算。

## 数据模型

| 表                        | 内容                                                                       |
| ------------------------- | -------------------------------------------------------------------------- |
| `prices`                  | 每个模型的四档单价与生效时间                                               |
| `usage_records`           | 每次调用的 `request_id`、用户、模型、四档 token、费用、状态与时间          |
| `ledger`                  | 余额变动流水：类型（充值/扣费/套餐/调整）、金额、幂等键、关联 `request_id` |
| `balances`                | 每个用户的当前余额与套餐剩余额度（派生缓存）                               |
| `plans` / `subscriptions` | 套餐定义（含可用模型、额度、周期）与用户的套餐发放记录                     |

## 幂等与一致性

- 每次网关请求生成一个 `request_id`（客户端可用 `x-zcode-request-id` 头透传）。`usage_records` 与 `ledger` 都以它为幂等键。
- 预扣与结算成对出现：结算写实际费用，同时把状态从 `reserved` 改为终态，预扣占用的额度随即释放。
- **重复 request id 返回 409 `duplicate_request`**，不转发上游。这是客户端重试可以预期的业务结果，不是故障。
- 进程在转发与结算之间崩溃时，未结算的预扣由启动时的对账任务释放（滞留超过 30 分钟的记录会被标记为 `upstream_error` 并把费用归零）。
- 流式请求的 usage 出现在响应末尾，因此**必须 tee 响应流**，不能等流结束再决定是否转发。

### 两个事务边界（审计#7、#6）

"查可用额度"与"写预扣"之间、以及"改状态"与"扣套餐/记流水"之间都隔着 `await`。
分开执行会被并发请求穿插，导致超支或以终态记录却没有记账。因此这两段都收进 SQLite 的单条
`BEGIN IMMEDIATE` 事务，由 sqlite 层提供原子方法：

```
预扣（reserveForRequest）——单事务，写锁内完成：
  ① 查 request_id 是否存在        → 存在 ⇒ duplicate（409，不转发）
  ② 读 balance、SUM(reserved)、有效订阅 remaining
  ③ 可用额度 < 预扣               → insufficient_balance（402，不转发）
  ④ INSERT usage_records(reserved, cost=预扣)  → 提交；随后才转发上游

结算（settleWithBilling）——单事务：
  ① UPDATE usage_records SET 用量/费用/终态 WHERE status='reserved'
       changes = 0 ⇒ 已结算过，直接提交，不记账（幂等）
  ② 扣套餐：有效订阅 remaining 足够则全额抵扣，否则扣到 0
  ③ 余额抵扣：min(剩余费用, 真实 balance)（真实余额封顶，不用可用额度——
     本请求的预扣不是实际扣款，用可用额度会把预扣重复算进封顶，审计#8）
  ④ INSERT ledger(usage, −余额抵扣) 与 UPDATE balances 在同一事务
  任何一步异常 ⇒ 整笔 ROLLBACK：用量记录仍停在 reserved，预扣仍然占用额度，
  由启动对账的滞留预扣释放兜底，不会出现"状态已是终态但没记账"的中间态。
```

结算失败不改变已经返给客户端的上游响应：上游费用已经发生，记账失败是平台侧问题。
流式与非流式都不因此给用户 500，记录保持 reserved，由滞留预扣释放兜底。

## 实现中确定的口径

以下几条是实作时定下来的，容易在后续改动中被破坏，因此写进 spec：

1. **余额非负是硬约束**（`balances` 上有 CHECK）。预扣按 `max_tokens` 估算，实际费用可能超出估算；
   此时**按真实余额封顶扣减**（审计#8：封顶要用真实余额，不能用"余额 − 预扣 + 套餐"的可用额度，
   本请求自己的预扣不是实际扣款，用它会把封顶算低），差额不计入余额，而是写进流水备注
   （"实际费用超出余额 X，已按余额扣减"）。预付费系统无法事后追缴，
   把它扣成负数只会让用户看到一个 500 而且账目也没记上。用量记录里保留的是**真实费用**，
   便于事后核对平台承担了多少。
2. **套餐额度优先，余额兜底**：一次调用的费用先扣套餐 `remaining_micros`，不足部分再扣余额。
   `ledger` 只记录**余额**的变化，因此恒等式 `SUM(ledger.amount) === balances.balance_micros`
   始终成立，可随时用管理后台的「对账」按钮验证。
3. **余额为 0 的用户也必须被拦住**：预扣额有下限（1 微元），否则零余额请求会穿透到上游让平台付费；
   但有有效套餐额度的用户例外（审计#5，见计费口径）。
4. **成本计算向上取整**（微元级），宁可多收 1 微元也不让平台因舍入少收。
5. **管理员调整金额不允许把余额扣成负数**：同一条 CHECK 约束会让整笔事务回滚，
   避免"调整成功但余额没变"这类静默失败。
6. **目录的 revision 以内容里声明的值为准**，不另起自增计数：客户端按内容里的 revision
   判断是否应用，而下载地址由 revision 拼成，两者必须是同一个数。
7. **预扣估算包含输入**（审计#9）：输出按 `max_tokens`（未声明时用默认上限），
   输入按请求体字节数 ÷ 4 粗估。只按输出估算会让长输入的预扣远低于实际费用，
   拦不住接近零余额的用户。默认输出上限是 32768 token（`ZCODE_PLATFORM_OUTPUT_TOKEN_CAP`
   可覆盖，0 表示不限制）。
8. **2xx 响应但拿不到用量时按预扣金额计费**（审计#2）：上游只返回完成内容、没带 usage 时不能按 0 记账。
   此时 usage 记录写 `ok`，`error_message` 标注"上游用量缺失，按预扣金额计费"，按预扣额扣费。
   4xx/5xx 是上游明确失败，不兜底，仍记 0 费用。
9. **OpenAI 兼容流式必须显式请求用量**（审计#2）：转发前对 `stream:true` 的 `/chat/completions`
   请求体注入 `stream_options.include_usage=true`（已有该字段时保留其它字段不动）。
   Responses API 的用量在 `response.completed` 事件的 `payload.response.usage` 里，解析器同时认。
10. **转发给上游的请求头是白名单**（审计#13）：只带 `content-type`、`accept`、
    `anthropic-version`、`anthropic-beta` 与 `openai-` 前缀的头；`cookie`、`user-agent`、
    `x-forwarded-for`、`cf-*`、`x-zcode-request-id`、客户端自带的认证头一律不转发。
    上游认证只由平台注入（anthropic → `x-api-key`，其余 → `authorization: Bearer`）。
11. **上游超时是"无数据超时"而非总时长**（审计#14）：等待响应头与等待 body 分片共用同一个计时器，
    每收到一个分片就重置，默认 60 秒（`ZCODE_PLATFORM_UPSTREAM_IDLE_TIMEOUT_MS`）。
    长回答可以持续数分钟，只要还在出数据就不该被掐断；挂住不动的上游才需要 abort。

## 客户端需要的改动

**网关本身不需要客户端改动**：客户端拿到的 provider `baseUrl` 指向
`<平台>/api/v1/gateway/<providerId>`（OpenAI 兼容协议要带上 `/v1` 后缀，使 SDK 拼出
`/chat/completions`），网关按白名单把已知路径转发到上游。
唯一的前提是构建客户端时把平台地址烘进产物（见 [release-update.md](release-update.md)）。

认证复用平台会话令牌：`Authorization: Bearer <登录令牌>`，客户端不必持有第二份凭据。

## 余额与套餐的展示

客户端已有的额度面板、余额卡片、重置倒计时 UI 全部复用：实现一个新的 `IUsageStatsService`，返回既有的 `UsageEntitlementSnapshot` / `UsageQuotaSnapshot` 结构，注册点只有一处（`packages/services/src/node.ts` 中创建 usage-stats 服务的位置）。

注意两个编译期常量需要小改以容纳平台自有的 provider id：`shared/src/model-provider-types.ts` 的白名单、`shared/src/plan-identity.ts` 的状态枚举。客户端展示只是 UX，**不是授权依据**。

## 边界

- 只对经网关的流量计费。用户自带 key 的 provider 直连上游，不计费，也不进入平台用量记录。
- 按套餐限制"模型可见性"做不到细粒度：模型目录是全站共享的一个 JSON。本期采用**模型可见、调用时由网关拒绝**的方式；若将来需要按套餐隐藏模型，需要改客户端走账号覆盖机制。
- 不做自动续费、优惠券、发票、多币种。

## 验收

1. 正常调用后，管理后台可见该次调用的 token 明细与费用，金额与单价表一致。
2. 余额置零后调用返回 402，且**上游没有收到该请求**；有套餐额度的用户不受此限（审计#5）。
3. 管理员充值后，客户端无需重启即可继续调用。
4. 同一 `request_id` 重复提交不会重复扣费，且 409 后不转发上游。
5. 套餐额度未用尽时优先扣额度，用尽后开始扣余额。
6. 流式与非流式请求都能正确计量；OpenAI 兼容流式转发前已注入 `include_usage`。
7. 用户把 baseUrl 改成本机地址时请求不携带网关令牌。
8. 白名单外的路径返回 `404 path_not_allowed`；未配单价的计费模型返回 `403 model_not_priced`（审计#3、#4）。
9. 上游 2xx 但没带 usage 时按预扣额扣费并标注原因；4xx/5xx 不产生费用（审计#2）。
10. 并发发起多笔请求时，可用额度不足的请求会被事务拦下，不会同时穿透（审计#7）。
11. 结算中途失败时整笔回滚，用量记录保持 `reserved`，不会出现"已改终态但没记账"（审计#6）。
12. 客户端登录 → 管理员配置 provider 与单价 → 带 `Authorization: Bearer` 调网关，余额按实际用量扣减（端到端）。
